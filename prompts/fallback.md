# Fallback — 未知・複雑・実装できない依頼にも価値ある結果を返す

## 目的

「すべての依頼を完璧に実装する」ことを目指さない。**何を実現したいかを理解し、その場で見られる最小単位まで縮小**する。ただし未実装を隠さない。

## 代表的なケースと対処

| ケース | 処理 | 正直な表示 |
|---|---|---|
| 要求が大きすぎる（例：Minecraftを作って） | 1つの操作できる要素（グリッドにブロックを置く等）に縮小 | 「ブロック配置のミニデモ」 |
| 外部API・認証・実データが必要 | 架空データでUIとローカル操作だけ見せる | 「サンプルデータ／外部連携なし」 |
| 特殊なゲームルールを短時間で実装しづらい | 判定可能な小部分だけ実装。ルール未対応を説明 | 「基本操作版。特殊ルールは未実装」 |
| 文章や企画の依頼 | カード／1枚企画書など読みやすく表示し、テキストも提供 | 「企画案／下書き」 |
| 要求の意味が複数に割れる | `questions.md` に従い最大1問。未回答なら安全な既定値 | 「まず○○版を作ります」 |
| ツールが存在しない／実行できない | ソースや画面案を出すが、確認済みとは呼ばない | 「未検証プロトタイプ／コンセプト」 |
| 危険・無権限の外部操作 | 実操作は行わず、ローカルの疑似フローに限定。必要なら断る | 「外部送信は行っていません」 |

## 代替案の作り方

1. 来訪者の言葉から核となる**行動動詞**を1つ抽出する（遊ぶ・入力・比べる・生成・承認）。
2. その動詞を1回体験できる最小の画面／機能に縮める。
3. その操作が可能なら **動作するミニデモ**として検証する。
4. 機能が実装できないなら**静的な画面案／構想**とラベル付けする。
5. 変更提案は「次は○○を足せます」に留め、すでにある機能のように言わない。

## 推奨フレーズ

- 「まずはすぐ触れる **○○版** を作ります。」
- 「外部サービスとは接続せず、**架空データで操作を試せる形**にします。」
- 「こちらは**画面案**です。送信や保存は行っていません。」

避ける：「全部できました」「本番運用できます」「保存しました」「AIが自動で送りました」（実際に確認・実行していない場合）。

## 制限時間内に完成しそうにないとき

新しい機能を足すのをやめ、現状の最重要操作の確認と表示に集中する。未完のまま完成を宣言せず、可能な範囲を示す。実行環境に停止・時間上限があるなら必ず従う。
